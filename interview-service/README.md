# Interview Service

Standalone FastAPI service for an adaptive interview MVP. It accepts CV and JD as JSON, owns the interview lifecycle, and does not access the Recruitment System database or auth layer directly.

## Run locally

```powershell
cd interview-service
Copy-Item .env.example .env
.\run.ps1
```

`run.ps1` reuses the repository's `ai-service\.venv`. If it does not exist,
install Python 3.10+ and use these commands instead:

```powershell
py -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app:app --reload --host 127.0.0.1 --port 8010
```

Open Swagger at `http://127.0.0.1:8010/docs`.

Start Candidate Web in a second terminal:

```powershell
cd ..\interview-web
.\run.ps1
```

Candidate Web runs at `http://127.0.0.1:4174`. Set the same address in
`INTERVIEW_WEB_ORIGIN`. The internal API contract is documented in
[`ONLINE_INTERVIEW_API.md`](ONLINE_INTERVIEW_API.md).

Set `GEMINI_API_KEY` in `.env` to use Gemini for adaptive follow-up questions. Without it, the service deliberately uses a deterministic fallback generator so the demo remains usable and testable.

## Google Cloud Speech-to-Text and Text-to-Speech

Enable the Cloud Speech-to-Text and Cloud Text-to-Speech APIs and create a
service-account JSON key. Set `INTERVIEW_SPEECH_PROVIDER=google` and point
`GOOGLE_APPLICATION_CREDENTIALS` to that file. Keep the JSON key on Interview
Service only. On Render, upload it as a Secret File and use
`/etc/secrets/<filename>.json` as the credential path.

Candidate Web records video as WebM for storage and separately captures a 16 kHz
mono PCM WAV stream. At the end of each answer it sends the WAV to the service,
which calls Google Cloud STT and then sends the transcript to the LLM. Question
audio is generated by Google Cloud TTS and returned as MP3. Browser
`SpeechRecognition` and `speechSynthesis` are not used.

Azure remains available as an optional fallback by setting
`INTERVIEW_SPEECH_PROVIDER=azure`, `AZURE_SPEECH_KEY`, and
`AZURE_SPEECH_REGION`.

## Completion callback

Pass `callback_url` when Recruitment System creates an interview. On
`COMPLETED`, `TERMINATED`, or `EXPIRED`, the service persists a callback event
and delivers it in the background. Failed deliveries survive service restarts
and retry with backoff up to `INTERVIEW_CALLBACK_MAX_ATTEMPTS`.

Every callback includes an event ID, Unix timestamp, and HMAC-SHA256 signature.
Recruitment System must verify the signature against the exact raw request body,
reject stale timestamps, and handle `event_id` idempotently. Configure the same
strong `INTERVIEW_CALLBACK_SECRET` in both systems. Use
`INTERVIEW_CALLBACK_ALLOWED_HOSTS` to restrict outbound callback destinations.

The service waits briefly for the final background video upload before notifying
Recruitment System. Callback state and manual retry are available through the
internal report and callback retry endpoints documented below.

## Supabase (recommended for online MVP)

1. Create a Supabase project and run
   [`supabase/migrations/20260912_online_interviews.sql`](supabase/migrations/20260912_online_interviews.sql)
   in its SQL Editor (or apply it with the Supabase CLI).
2. Put `SUPABASE_URL` and the **server-only** `SUPABASE_SERVICE_ROLE_KEY` in
   `interview-service/.env`.
3. Keep `SUPABASE_INTERVIEW_BUCKET=interview-videos`. The migration makes this
   bucket private and allows only WebM/MP4 up to 50 MB.

When configured, the service stores interview JSON in `public.online_interviews`
and video objects in the private bucket. The candidate web receives neither a
Supabase credential nor a storage URL; only the internal, key-protected video
endpoint can read a recording. Without these variables, the service deliberately
falls back to local SQLite and `private-media` for offline development.

## Recruitment System integration

Use the independent `/v1/internal/interviews` API described in
[`ONLINE_INTERVIEW_API.md`](ONLINE_INTERVIEW_API.md). It creates a one-time
candidate link and does not require the Interview Service to read the
Recruitment System database.

For production, use the Supabase configuration above. Local recordings are stored
under `private-media/<session-id>/` and local state in `data/interviews.sqlite3`,
both ignored by Git.
